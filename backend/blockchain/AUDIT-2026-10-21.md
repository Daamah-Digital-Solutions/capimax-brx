# Capimax BRX — Smart-contract & chain-layer security audit (internal)

**Date:** 2026-10-21 · **Scope:** `PropertyToken.sol`, `PropertyTokenFactory.sol`, the Django chain layer (`apps/chain`, custodial key handling in `apps/wallets`, every on-chain call site) and the testnet deployment/ops setup.
**Purpose:** pre-mainnet review requested by the client.
**Not a substitute for:** an independent third-party audit. This is an internal review by the platform's own engineering; the contracts still carry the "UNAUDITED" notice in their source, and that notice should only be removed after an external firm signs off.

## 1. Summary

The contract code itself is small, standard and clean: OpenZeppelin 5.6.1 `ERC20` + `AccessControl` for the token (0 decimals, hard supply cap, mint restricted to `MINTER_ROLE`) and an `Ownable` factory that deploys one token per property and refuses duplicate slugs.

| Check | Result |
|---|---|
| Slither 0.11.6, 102 detectors, solc 0.8.24 | **0 findings** |
| Hardhat test suite (`npx hardhat test`) | **16 / 16 passing** |
| `npm audit --omit=dev` (contract dependencies) | **0 vulnerabilities** |
| Reentrancy / unchecked external calls / payable sinks / overflow | none present (no external calls except `new PropertyToken`, no `receive`, Solidity ≥0.8 checked math) |
| Live testnet state (read-only, BSC Testnet 97) | factory `0xff92855263344C6Bb808fDCBb67D9Af39ed14bAc`, 12 tokens deployed, every token's `DEFAULT_ADMIN_ROLE` and `MINTER_ROLE` held by the factory owner, supplies within caps |

**No vulnerability was found in the contract code.** The findings below are about *what the contracts and the operating setup lack for mainnet*: every power sits in one hot key, there is no emergency stop and no on-chain way to reverse a holding, and the backend's transaction handling has reliability gaps that cost real money on mainnet. None of these matter much on testnet; all of them matter with real funds.

Severity scale: **High** = must be resolved before mainnet · **Medium** = should be resolved before mainnet · **Low** = fix when convenient · **Info** = note.

## 2. Findings

### H-1 · One hot EOA holds every power (owner, admin, minter, gas sponsor)
**Where:** `PropertyTokenFactory` constructor / `deployPropertyToken` (`owner()` becomes `DEFAULT_ADMIN_ROLE` + `MINTER_ROLE` on each child); `apps/chain/client.py` (`DEPLOYER_PRIVATE_KEY`); live state: factory owner `0xd442bEbC…` is a plain EOA (no code).
**Risk:** the same key that signs every user purchase (mint) from a web server also owns the factory and administers every token. If the server or the `.env` is compromised, the attacker can mint the entire unsold supply of every property to themselves, deploy junk tokens, and there is nothing a second party can do — the attacker *is* the admin, so roles cannot be taken back.
**Recommendation:**
1. Move `DEFAULT_ADMIN_ROLE` and factory ownership to a multisig (Gnosis Safe, 2-of-3 or better) held by the client's directors.
2. Keep a separate low-balance **hot minter key** on the server with `MINTER_ROLE` only. The Safe can revoke it at any time.
3. This needs a small contract change: the factory should take the minter address separately (e.g. an owner-settable `minter` on the factory, granted `MINTER_ROLE` on each new token, with `DEFAULT_ADMIN_ROLE` going to the owner), and ideally an `OPERATOR`/deployer role so the server can still deploy tokens while the Safe owns the factory. Today, if the factory were simply transferred to a Safe, every property deployment would have to be signed manually in the Safe.
4. Use `Ownable2Step` on the factory (ownership transfer must be accepted; a typo cannot brick it).

### H-2 · No emergency stop and no on-chain reversal (pause / clawback / burn)
**Where:** `PropertyToken` has `mint` only. `apps/installments/services.py::default_plan` documents "NO on-chain clawback": forfeiture is ledger-only.
**Risk:** (a) if a key leaks or a bug is found there is no `pause()`; (b) a defaulted installment plan leaves the forfeited units physically in the investor's custodial wallet while the ledger removes them — the on-chain record and the legal record disagree; (c) the ledger "frees" those units for resale but `totalSupply` on chain still counts them, so once forfeiture is enabled the freed units can push a later mint past `maxSupply` and the purchase reverts with "cap exceeded".
**Today's exposure:** low — `INSTALLMENT_FORFEIT_ENABLED` is not set on the server (defaults to off) and wallets are fully custodial.
**Recommendation:** add `ERC20Pausable` (admin-only `pause`/`unpause`) and an admin-only `clawback(from, to, amount)` (or `burnFrom` + re-mint) used by forfeiture and by any future compliance action. This is the standard pattern for custodial security tokens. Decide explicitly, in writing, whether the chain or the ledger is the record of truth, and make the other one follow it.

### H-3 · Deployer nonce race under concurrency
**Where:** `apps/chain/service.py::_base_tx_params` uses `get_transaction_count(address, "pending")`; `mint`, `deploy_property_token` and `_fund_gas_if_needed` all sign with the one deployer key; the API runs **3 gunicorn workers**, and `reconcile_investments` / `process_transfers` cron jobs sign with the same key.
**Risk:** two purchases (or a purchase and the cron) that reach the chain at the same moment read the same pending nonce; one transaction fails ("nonce too low" / "replacement underpriced"). The code handles it safely (the DB rolls back, nothing fake is recorded) but the buyer's purchase fails and must be picked up by reconcile — on mainnet that is a paid customer whose units did not arrive, and a wasted gas fee.
**Recommendation:** serialize all deployer-signed transactions through one place — a DB advisory lock (`pg_advisory_xact_lock`) around build+send, or a single queue worker that owns the nonce. Add a retry on nonce errors.

### M-1 · Receipt timeout vs. a transaction that still mines
**Where:** `_send` waits 180 s then raises `TransactionError`; callers roll back the DB.
**Risk:** on a slow RPC the transaction can be mined *after* the timeout: the chain moved, the ledger did not. For **mint** this is mitigated well — `reconcile._chain_holds_more_than_ledger` refuses to mint again and flags the investment for review. For **transfers** (secondary market, LP market, gifts) there is no such check: a retry would send the seller's units a second time (the ledger moved once, the chain twice).
**Recommendation:** before any transfer retry, compare the chain balance with the ledger as reconcile does for mints; store the tx hash *before* waiting for the receipt (pending state) so a timed-out hash can be looked up instead of re-sent; raise the timeout or poll the hash in reconcile.

### M-2 · One confirmation is treated as final
**Where:** `_send` returns on `wait_for_transaction_receipt` (first inclusion).
**Risk:** a chain reorg after the DB recorded the mint. BSC's fast finality makes this rare, but mainnet mints are paid purchases.
**Recommendation:** wait for the block to be *finalized* (or N ≥ 15 confirmations) before marking an investment minted, or record "minted-pending" and finalize in reconcile.

### M-3 · Secrets: the deployer key, the wallet-encryption key and the database share one trust boundary
**Where:** `/opt/capimax-brx/backend/.env` (root, 0600, loaded by systemd) holds `DEPLOYER_PRIVATE_KEY` **and** `WALLET_ENCRYPTION_KEY`; every custodial private key is Fernet-encrypted in the same server's Postgres; a plaintext copy of `.env` exists in `/root/backups/env.2026…` (root, 0600). `KEY_MANAGER_BACKEND=fernet-db`.
**Risk:** root on the VPS = the platform key + every user's key. The `keys.py` design ("a DB dump alone is useless") holds only while the env file is not next to the DB. There is no key-rotation command for the Fernet key or for the deployer key (rotating the deployer means granting roles on every existing token from the old key).
**Recommendation:** for mainnet move both keys out of the file: a KMS/HSM-backed `KeyManager` (the abstraction already exists) for custodial keys, and the hot minter key in a secret manager or an external signer; delete the `.env` copy from `/root/backups` or move it to the offsite encrypted backup; write the rotation runbook before launch (H-1's design makes rotation a Safe action instead of N transactions).

### M-4 · Tokens are freely transferable (no allowlist)
**Where:** `PropertyToken` is a plain ERC20; any holder can `transfer` to any address, any address can hold.
**Risk:** none today — all wallets are platform-custodial and KYC-gated off chain. It becomes a compliance problem the moment a key leaves custody (export, self-custody, a leaked key): units could move to non-KYC addresses and the ledger would not know.
**Recommendation:** decide before mainnet. Either keep custody closed (document it; never offer key export) or add a transfer allowlist (ERC-1404 / ERC-3643 style `canTransfer` with an admin-managed registry).

### L-1 · Mainnet details hardcoded to testnet
`_explorer()` returns `testnet.bscscan.com` links (they would be wrong in receipts/certificates on mainnet); the RPC setting is named `BSC_TESTNET_RPC_URL`; `hardhat.config.js` defines no mainnet network (deliberate) and `scripts/deploy.js` also deploys a demo token "1" (must not run on mainnet). The chain-id guard in `require_connection` is good and must stay.

### L-2 · Floating pragma and unconfirmed source verification
`pragma solidity ^0.8.24` — pin to `0.8.24` so the verified bytecode is reproducible. Source verification on the explorer could not be confirmed automatically (BscScan sits behind a bot-check wall for scripts); verify factory and token source on mainnet and keep the exact compiler settings (0.8.24, optimizer 200 runs) in the runbook.

### L-3 · Gas cost controls
`gasPrice = w3.eth.gas_price` with no ceiling; the platform pays gas for every custodial transfer via `_fund_gas_if_needed` (gifts have `GIFT_FEE_PERCENT=0`, so many tiny gifts cost the platform gas). Add a gas-price cap, a low-balance alert on the hot key (today 0.297 tBNB), and a rate limit on gift deliveries. Use a dedicated/paid RPC with a fallback instead of the public endpoint.

### Info
- `nominalPriceUsd` and name/symbol lengths are not validated on chain (backend always passes 100 / ≤60 chars); `_token_symbol` can collide across slugs (cosmetic — the registry key is the slug).
- Hardhat test gap: no test for role revocation, for `transferOwnership` of the factory, or for the `allTokens` view — add with the H-1 changes.
- Who can trigger on-chain actions is correctly gated: deploy only from Django-admin actions (`owner/admin.py`, `properties/admin.py`) or management commands; mint only after a provider-verified payment inside a row lock; the mint amount is server-computed from the paid amount.
- Custodial signer handling is careful (decrypt → sign → drop; nothing logged). The private key persists in the signer object until garbage-collected, which is acceptable for a Python process.

## 3. What mainnet needs, in order

1. **Contract changes (H-1, H-2, L-2):** factory `minter`/operator separation, `Ownable2Step`, `ERC20Pausable`, admin `clawback`; pin the pragma; extend the tests. Then the **external audit** on the final source.
2. **Key custody (H-1, M-3):** Safe multisig as owner/admin; hot minter key only on the server; KMS-backed `KeyManager`; rotation runbook; remove the env copy from local backups.
3. **Backend transaction handling (H-3, M-1, M-2):** global lock/nonce queue, pending-hash recording, finality wait, chain-vs-ledger check before transfer retries.
4. **Policy decision (M-4, H-2):** custody-only vs. allowlist; chain-or-ledger as record of truth; forfeiture on chain.
5. **Runbook (L-1, L-3):** mainnet hardhat network, verified source, explorer/RPC settings, gas cap, low-balance alerts, paid RPC with fallback, BNB funding plan for the hot key.

## 4. Status of the fixes (same day)

| Finding | Status |
|---|---|
| **H-1** one key for everything | **Fixed in code.** Factory: `Ownable2Step` owner (multisig), `isOperator` (server deploys tokens), `minter` (hot key, owner-settable, applies to new tokens). Token: admin = owner (admin + pauser + controller), minter = hot key (minter + pauser only). Backend: new `CHAIN_ADMIN_ADDRESS` setting = factory owner; empty means the deployer (test networks). **Open:** the Safe address and its signers (client decision). |
| **H-2** no pause / clawback | **Fixed in code.** `pause` (hot key or admin), `unpause` (admin only), `clawback(from, to, amount, reason)` (controller only, works while paused; `to = 0x0` burns and frees the cap). Backend: `service.pause/unpause/clawback/is_paused/has_role`, `manage.py chain_pause`, mints and transfers refuse a paused token before sending, installment forfeiture burns on chain when the server key holds the controller role (otherwise logs that the multisig must do it). |
| **H-3** nonce race | **Fixed.** Every send goes through `_transact`: Postgres advisory lock per signing address held from nonce read to receipt, one retry on a nonce rejection. Measured on a local chain: 8 simultaneous mints → 4 failed without the lock, 0 with it. |
| M-1 … L-3 | Open (next steps). |

Verification: Slither 0 findings (16 contracts, 102 detectors); Hardhat 24/24 (role split, two-step ownership, pause permissions, clawback while paused, burn frees cap, revoke a leaked minter, size < 24 KB); Django chain tests 30/30; an integration run of the real backend code against a local Hardhat chain (factory with a separate admin, operator deploy, concurrent mints, pause, refused unpause/clawback for the hot key, admin burn while paused, unpause, delegated controller).

**Live testnet:** unchanged. The 12 tokens already deployed predate these controls (`is_paused` returns `None` for them and the backend keeps minting as before); the new contracts are for mainnet. A dry-run deployment of the new factory to testnet can be done separately without switching the live properties.

## 5. Method
Manual review of both contracts and all backend call sites; Slither 0.11.6 with solc 0.8.24; Hardhat 2.28.6 test suite; `npm audit`; read-only RPC inspection of the live testnet factory and tokens (owner, roles, supplies, caps); server configuration inspected for file ownership/permissions and process layout only — secret values were never read.
